## 3. 어떤 스킬과 명령을 쓰는가

일상적으로 사람이 요청할 진입점은 네 가지다. 스킬 요청은 에이전트 대화에서 하고, 셸 명령은 터미널에서 실행한다.

| 목적 | 에이전트에게 할 요청 | 결과와 확인 사항 |
|---|---|---|
| 요구 등록 | `todo [원하는 변경과 기대 결과]` | 범위·조건·근거를 가진 문서와 실제 트랙 ID를 확인한다. |
| 후보 추천 | `trackpicks` | 내부 스킬 폴더 이름은 `track-picks`다. 추천 사유·의존성·충돌을 읽는다. 실행은 시작하지 않는다. |
| 선택한 작업 실행 | `trackrun [실제 ID]` | 설치된 셸 명령이기도 하다. 실행 요청과 드라이버 기동을 함께 한다. |
| 관찰 재평가 | `watchlist` | 조건 변화·근거·후속 행동을 검토한다. 새 후속 트랙은 다시 선택해야 한다. |

동봉 스킬은 총 9개다. 위 네 진입점 외에 `track-run`, `track-work`, `track-review`, `track-land`, `track-triage`가 역할별 절차를 제공한다. 이를 모두 새 전역 스킬로 복사할 필요는 없다. 대상 프로젝트에 제공된 설치 명령으로 배치하고 상태 경로와 연결한다.

55번 소스의 `.agents/skills`는 원래 `../skills`를 가리키는 링크다. 실제 업무 프로젝트용 설치 경로와 혼동해 덮어쓰지 않는다. 스킬이 현재 대화에 보이지 않으면 설치된 `SKILL.md`를 직접 읽게 하거나 새 세션에서 확인한다.

## 5. 등록 → 선택 → 실행

### 등록: 접수함에 문서를 넣는다

```text
todo 일시적인 네트워크 오류만 제한적으로 재시도하도록 바꾸고 테스트해 주세요.
재시도 횟수·대기 시간·재시도하지 않을 오류·성공 조건을 문서에 명시해 주세요.
우선 등록까지만 하고 실제 ID와 문서 링크를 보여 주세요.
```

문서의 목표, 제외 범위, 검증 조건, 변경 허용 파일을 읽는다. 등록 문서를 수정할 때는 정본 파일을 직접 덮어쓰지 않고 새 리비전을 등록한다. 직접 등록하는 경우의 형식은 다음과 같다.

```sh
todo-flow --state "$FLOW_STATE" register /absolute/scratch/track.html
todo-flow --state "$FLOW_STATE" register /absolute/scratch/revised.html --expected-revision 2
```

경로와 리비전 `2`는 예시다. 현재 리비전을 먼저 읽고 실제 값으로 바꾼다. 이미지 등 자산이 있으면 `--assets`를 사용한다.

### 선택: 할 일을 고르되, 실행과 구분한다

에이전트에게 `trackpicks`를 요청하거나 대시보드에서 선택한다. 추천은 승인도 실행도 아니다. 대시보드는 선택한 `trackrun` 명령을 복사하며 직접 실행 요청을 보내지 않는다.

대시보드가 필요하면 준비된 프로젝트 상태를 지정해 별도 터미널에서 실행한다.

```sh
todo-flow --state "$FLOW_STATE" serve --port 8765
```

접속 주소는 `http://127.0.0.1:8765`다. 다른 프로젝트는 다른 포트를 사용한다. 포트 충돌 때문에 다른 서버를 종료하지 않는다. 문서 URL의 ID·리비전은 실제 등록 결과를 사용한다. UI 언어 전환은 표시만 바꾸며 워커 언어나 기존 문서를 번역하지 않는다.

### 실행: 승인된 실제 ID만 지정한다

```sh
trackrun --state "$FLOW_STATE" ACTUAL_TRACK_ID --jobs 2
```

`ACTUAL_TRACK_ID`를 실제 ID로 바꾼다. `--jobs 2`는 한 드라이버에서 동시에 처리할 작업 상한이지 선택 가능한 트랙 수가 아니다. 여러 드라이버가 전역 상한을 공유하지 않으므로 임의로 드라이버를 늘리지 않는다.

`--request-only`는 요청만 기록한다. 별도 드라이버가 없다면 진행하지 않는다. 기본 `auto` 실행기는 가능한 Orca·설정 터미널·기존 tmux를 우선하고, 그 경로가 없으면 headless를 사용한다. 명시한 실행기가 불가능하거나 시작 여부가 불명확하면 중복 실행하지 말고 시도 기록부터 확인한다.

## 10. 시작 전 확인 질문

- 등록한 문서를 읽었는가? 실제 실행 ID와 성공 조건을 말할 수 있는가?
- 도구 소스 55번과 변경할 업무 프로젝트를 구분했는가?
- 실행 어댑터·모델 정책과 커밋·원격 게시 권한이 확인됐는가?
- `review`에서도 커밋·PR 게시가 가능함을 이해했는가?
- 중단 시 어느 상태 폴더와 어떤 결과·효과 기록을 확인할지 아는가?

처음 사용할 때는 위 4절의 “준비까지만” 요청문으로 대상 프로젝트 연결 조건부터 확인한다.
